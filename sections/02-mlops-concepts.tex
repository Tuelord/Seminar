\section{MLOps Concepts}
\label{sec:mlops-concepts}

Kreuzberger et al.\ define MLOps as a paradigm of best practices,
concepts and development culture for the end-to-end conceptualisation,
implementation, monitoring, deployment and scalability of ML products,
realised through principles such as CI/CD automation, continuous training
and monitoring, and components such as a feature store and a model
registry~\cite{kreuzberger2023mlops}. This section defines the six
concepts used in this report and gives the Michelangelo counterpart of
each.

\subsection{ML Lifecycle}
\label{subsec:ml-lifecycle}

The \emph{ML lifecycle} is the sequence of activities needed to build and
operate a model. Amershi et al.\ describe nine stages, from model
requirements and data collection through feature engineering, training
and evaluation to deployment and monitoring, and stress that the process
is non-linear: monitoring results often send work back to earlier stages,
for example to collect new data~\cite{amershi2019software}.
\textbf{In Michelangelo}, the lifecycle is condensed into a six-step
workflow shared by almost all use cases~\cite{delbalso2017meet}
(\Cref{subsec:six-step-workflow}).

\subsection{CI/CD and Continuous Training}
\label{subsec:cicd-ct}

\emph{CI/CD} automates building, testing, delivery and deployment.
ML adds \emph{continuous training} (CT): periodic retraining on new data,
triggered through monitoring and a feedback loop and always followed by
an evaluation of the new model~\cite{kreuzberger2023mlops}.
\textbf{In Michelangelo}, early teams scheduled retraining and
redeployment through the platform API~\cite{delbalso2017meet}. Gallery
later allowed rules over stored metrics to detect drift and retrain
individual models, such as a single city's
model~\cite{sun2020gallery}. Since 2020, Project Canvas has provided
full ML CI/CD: model code and configuration live in a monorepo, are
packaged into immutable Docker images and are deployed automatically
after tests and validation~\cite{wang2024predictive}.

\subsection{Feature Store}
\label{subsec:feature-store}

A \emph{feature store} centralises commonly used features, combining an
offline store for experimentation and training with a low-latency online
store for inference~\cite{kreuzberger2023mlops}. It avoids duplicated
feature engineering and inconsistent feature definitions across
teams~\cite{orr2021managing}.
\textbf{In Michelangelo}, the feature store (later \emph{Palette}) keeps
offline features in Hive and online features in Cassandra, computed by
Spark batch jobs or Samza streaming jobs~\cite{li2017scaling}. Models
refer to features only by canonical name, and the platform resolves each
name to the correct offline or online source~\cite{delbalso2017meet}.

\subsection{Model Registry}
\label{subsec:model-registry}

A \emph{model registry} stores trained models together with metadata
such as parameters, metrics and lineage, enabling versioning and
reproducibility~\cite{kreuzberger2023mlops}.
\textbf{In Michelangelo}, each trained model is a versioned object
holding its configuration, data references, metrics and learned
parameters, and clients address models by UUID or
tag~\cite{delbalso2017meet}. This role was consolidated in
\emph{Gallery}, built by Uber's Marketplace Forecasting team and later
integrated into Michelangelo~\cite{sun2020gallery}. Gallery treats models
as immutable, so every update creates a new version; separates a
\emph{model} (its specification) from a \emph{model instance} (the
parameters learned from one training set); and uses a rule engine to
select a \emph{champion} model for serving or to trigger
deployment~\cite{sun2020gallery}. Within Michelangelo it manages more
than one million model instances~\cite{sun2020gallery}.

\subsection{Training/Serving Skew}
\label{subsec:train-serve-skew}

\emph{Training/serving skew} is a discrepancy between the data used for
training and the data seen in production. Its most common cause is
different code paths for generating the two datasets; it appears as
\emph{feature skew} (different feature values), \emph{distribution skew}
(different feature distributions) or \emph{scoring/serving skew} (only a
subset of scored examples is served, biasing future training
data)~\cite{breck2019data}.
\textbf{In Michelangelo}, each feature is computed by a single pipeline
for training and prediction~\cite{li2017scaling}, and transformations
are written in a feature DSL whose expressions are stored with the model
and applied identically in both paths~\cite{delbalso2017meet}.

\subsection{Monitoring and Drift}
\label{subsec:monitoring-drift}

Because the external world is rarely stable, ML systems require live
monitoring with automated response~\cite{sculley2015hidden}. A key reason
is \emph{concept drift}, a change in the joint distribution of inputs $X$
and target $y$ over time~\cite{gama2014survey}:
\begin{equation}
  \exists X : p_{t_0}(X, y) \neq p_{t_1}(X, y).
  \label{eq:concept-drift}
\end{equation}
\emph{Real} drift changes $p(y \mid X)$ and thus affects predictions,
whereas \emph{virtual} drift changes only the input distribution
$p(X)$~\cite{gama2014survey}.
\textbf{In Michelangelo}, when labels are available, predictions are
logged, joined with observed outcomes, and accuracy metrics are published
with threshold alerts~\cite{delbalso2017meet,li2017scaling}. When labels
are delayed or unavailable, the platform monitors the distributions of
features and predictions instead~\cite{delbalso2018scaling}, which
detects changes in $p(X)$ but not directly in $p(y \mid X)$. Model
quality targets introduced in Michelangelo~2.0 are discussed in
\Cref{subsec:strengths}.

\section{Overview of Michelangelo}
\label{sec:michelangelo-overview}

\subsection{Evolution from 2015 to 2024}
\label{subsec:evolution}

Uber began building Michelangelo in mid-2015~\cite{delbalso2017meet}.
\Cref{tab:timeline} summarises the three phases defined by
Uber~\cite{wang2024predictive}. Version~1.0 focused on predictive ML on
tabular data at large scale. Version~2.0 shifted from enabling ML
everywhere to improving high-impact projects, addressing four
shortcomings of 1.0: no model-quality definition or project tiering,
weak deep learning (DL) support, poor support for collaborative
development, and fragmented tooling~\cite{wang2024predictive}. The
generative AI phase extended the platform to large language models
(LLMs)~\cite{wang2024predictive}.

\subsection{The Six-Step Workflow}
\label{subsec:six-step-workflow}

Michelangelo provides tooling for a six-step workflow
(\Cref{fig:workflow})~\cite{delbalso2017meet}, illustrated here with the
UberEATS estimated time of delivery (ETD) model:
\begin{enumerate}
  \item \textbf{Manage data:} compute offline features with Spark and
    Hive, and online features in batch or streaming into Cassandra. For
    ETD, a restaurant's average meal preparation time over seven days is
    a batch feature, while the same average over the last hour is a
    near-real-time feature~\cite{delbalso2017meet}.
  \item \textbf{Train:} run distributed training jobs from a model
    configuration; \emph{partitioned models} train one model per city and
    fall back to a country-level model when data is
    sparse~\cite{delbalso2017meet,li2017scaling}.
  \item \textbf{Evaluate:} store each model in the repository with
    accuracy and feature-importance reports for
    comparison~\cite{delbalso2017meet}.
  \item \textbf{Deploy:} deploy offline (batch scoring in Spark), online
    (a prediction service called via RPC) or as an embedded
    library~\cite{delbalso2017meet}.
  \item \textbf{Predict:} apply the stored DSL, fetch features from the
    feature store and score; ETD serving reaches a 99th-percentile latency
    of 20\,ms~\cite{li2017scaling}.
  \item \textbf{Monitor:} join predictions with outcomes and raise
    alerts (\Cref{subsec:monitoring-drift}).
\end{enumerate}
