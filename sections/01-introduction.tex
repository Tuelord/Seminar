\section{Introduction}
\label{sec:introduction}

Developing and deploying machine learning (ML) systems is relatively fast
and cheap, but maintaining them over time is difficult and expensive: in
a real-world ML system the model code is only a small part, surrounded by
infrastructure for data collection, feature extraction, serving and
monitoring~\cite{sculley2015hidden}. The ML workflow is also data-centric
and highly non-linear, with frequent feedback loops between
stages~\cite{amershi2019software}. \emph{Machine Learning Operations}
(MLOps) addresses this gap by combining ML, software engineering and
data engineering to bring ML products into production and keep them
there~\cite{kreuzberger2023mlops}.

This report studies MLOps from a \emph{software architecture} perspective,
using Uber's internal ML platform \emph{Michelangelo} as a case study.
Michelangelo was created to replace fragmented, team-specific ML tooling
with one standardised end-to-end workflow~\cite{delbalso2017meet}, and
has since evolved from predictive ML through deep learning to generative
AI~\cite{wang2024predictive}. We chose it for three reasons: it is one of
the earliest documented enterprise ML platforms, and its feature store is
described by authors involved in building it as the first industrial
feature store~\cite{orr2021managing}; its design is documented in both
peer-reviewed papers~\cite{li2017scaling,sun2020gallery} and candid
engineering reports spanning eight
years~\cite{delbalso2017meet,delbalso2018scaling,wang2024predictive}; and
its scale makes architectural trade-offs visible (\Cref{tab:timeline}).

The report is organised as follows. \Cref{sec:mlops-concepts} defines six
core MLOps concepts and maps each to Michelangelo, and
\Cref{sec:michelangelo-overview} summarises the platform's evolution and
workflow. \Cref{sec:design-rationale} derives its design decisions from
the problems Uber faced in 2015, \Cref{sec:pros-cons} evaluates its
strengths, weaknesses and trade-offs, \Cref{sec:layered-architecture}
analyses it as a layered architecture, and \Cref{sec:conclusion}
concludes.
